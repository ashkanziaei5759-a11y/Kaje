# کاژه — Kajeh

A restaurant costing and profitability platform. It exists to answer one
question, at any moment, for any dish on the menu:

> **این غذا دقیقاً چقدر برای کاژه تمام می‌شود، چند درصد سود دارد، چرا این‌قدر
> هزینه دارد، و قیمت فروش پیشنهادی آن چقدر است؟**
>
> *What does this dish actually cost, what margin does it earn, why does it cost
> that much, and what should it sell for?*

Not a POS, and not a calculator. A connected system where a supplier's invoice
moves through inventory, recipes, dish costs, recommended prices, sales and
reports without anyone re-keying a number.

---

## The chain

Everything is one loop. Each arrow is code, not a manual step:

```
supplier purchase
   ↓  approvePurchase()          weighted-average cost, price history, alerts
ingredient price
   ↓
inventory  (append-only ledger, StockLevel is its projection)
   ↓
recipe / BOM  (nested sub-recipes, yield and waste)
   ↓  costRecipe()
menu item cost  =  ingredients + sub-recipes + packaging + labour + overhead
   ↓  recommendPrice()
recommended selling price   (manual override always wins)
   ↓  confirmOrder()
sale  →  stock depletion  →  cost snapshot frozen at sale time
   ↓
reports: P&L, menu engineering, actual vs theoretical variance
```

The cost snapshot is what makes historical reporting honest. Ingredient prices
move weekly; a report that re-costs last month's sales at today's prices is
fiction. Snapshots are written once and never recalculated.

## Quick start

Requires Node 20+ and PostgreSQL 14+.

```bash
npm install
cp .env.example .env

# Set AUTH_SECRET — there is no development default, by design.
openssl rand -base64 32

createdb kajeh
npm run db:migrate      # apply schema + check constraints
npm run db:seed         # build the Kajeh demo restaurant
npm run dev
```

Open <http://localhost:3000>. The public menu is at `/menu` and needs no account.

## The costing engine

For each menu item:

```
  ingredient_cost          yield-adjusted, recursive through sub-recipes
+ sub_recipe_cost
+ packaging_cost
+ direct_labour_cost       configurable method
+ allocated_overhead       configurable method
= total_cost

  selling_price − total_cost           = gross_profit
  gross_profit ÷ selling_price         = gross_margin %
  ingredient_cost ÷ selling_price      = food_cost %
```

The worked example from the brief, reproduced by the test suite:

| | |
|---|---:|
| Ingredients | 280,000 |
| Labour (15 min × 2,000) | 30,000 |
| Packaging | 5,000 |
| Overhead (300M ÷ 10,000 units) | 30,000 |
| **Total cost** | **345,000** |
| Recommended at 30% target margin | 492,857 |

### Three decisions worth knowing about

**Recommended price divides, it does not multiply.**
`price = cost ÷ (1 − margin)`. Marking a 345,000 cost up by 1.3 gives 448,500,
which is a **23% margin, not 30%** — margin is measured against revenue, not
against cost. This is the single most common costing error in the industry.

**Rounding always goes up.** Rounding a recommendation to the *nearest* step
would let the rounding itself push an item below its target margin.

**Yield is charged against usable weight.** Ten kilos of meat that cleans down
to eight still cost what ten cost, so the eight carry the whole price. Costing
at the raw purchase price understates every dish built from it.

### Nothing is hard-coded

Tax, target margin, labour rate, overhead rate, allocation method, rounding
rule, minimum acceptable margin and currency all live on `CostingProfile` and
`Restaurant` rows. Labour supports per-minute, percent-of-revenue and per-unit
allocation; overhead adds percent-of-food-cost and per-labour-minute. Items can
use different profiles — the demo prices drinks through a separate profile,
because a flat per-unit overhead share is right for a main course and absurd for
a glass of tea.

When overhead is a percentage of revenue the calculation is self-referential —
price depends on cost, cost depends on price. The engine resolves it with a
fixed-point iteration that converges in a handful of passes, and there is a test
proving the settled price still hits the target margin.

## Architecture

```
src/lib/
  money.ts              Decimal money. No financial value is ever a JS float.
  units.ts              Dimensional (kg↔g) vs packaging (box→pieces) conversion
  jalali.ts             Jalali calendar, verified against ICU
  engine/
    cost-engine.ts      Recursive BOM costing, pricing, cycle detection
    inventory-engine.ts Weighted-average valuation, ledger arithmetic
    menu-engineering.ts Kasavana-Smith classification, cost variance
  auth/                 JWT sessions, role permissions

src/server/services/    Persistence. The only place StockLevel is mutated.
  purchasing.ts         Purchase → inventory → price history → alerts
  sales.ts              Order → depletion → cost snapshots
  costing.ts            Menu costing, auto sold-out, recipe versioning
  reports.ts            Dashboard and report aggregation

src/app/                Next.js App Router — 16 admin screens, 1 public menu
```

The engines are **pure functions over plain value objects** and never touch
Prisma. That makes them exhaustively testable without a database, reusable for
what-if simulation on unsaved data, and re-runnable against historical
snapshots.

### Data integrity

- **The ledger is the truth.** `StockLevel` is a cached projection of
  `InventoryTransaction`. Every mutation writes both, in one transaction. An
  integration test asserts they still agree after the whole test suite has run.
- **Transactional boundaries are all-or-nothing.** A purchase that received
  stock but failed to update prices would corrupt every dish costed afterwards,
  so there is no code path to a half-applied invoice.
- **The database enforces what the application enforces.** Check constraints
  cover the ingredient-XOR-sub-recipe rule, yield fractions staying in `(0,1]`,
  positive conversion factors and non-negative valuations.
- **Deletes that would destroy history fail loudly.** Stock rows do not cascade
  from a branch, and BOM lines hold `RESTRICT` references — deleting an
  ingredient a recipe still uses is refused rather than silently gutting the
  recipe.

### Multi-branch

Every business entity carries `restaurantId`; stock-bearing entities also carry
`branchId` and `warehouseId`. A second branch needs no migration of business
data. The UI stays single-branch to avoid complicating a one-restaurant setup.

## Localisation

Persian-first and RTL throughout, English-ready underneath. The Jalali converter
is implemented directly rather than pulled from a dependency, and a test checks
it against ICU's Persian calendar across 332 dates spanning a decade — it caught
two real bugs while being written.

Currency is a per-restaurant setting. Changing it changes every displayed amount
without rewriting a single stored value.

CSV exports carry a UTF-8 BOM so Excel opens Persian text rather than mojibake,
and use RFC 6266 `filename*` so the downloaded file keeps its Persian name.

## What is not built

Deliberately out of scope for this stage, with the schema shaped to accept them:

- **POS, tables, KDS, delivery.** `Order`, `OrderItem` and `OrderModifier` exist
  and are exercised by the sales service; what is missing is the operational UI.
- **Invoice OCR.** `Purchase.ocrRaw` and `ocrConfidence` are in the schema and
  the `PENDING_REVIEW` status exists for the human approval step, but no
  extraction is wired up.
- **Excel and PDF export.** CSV is implemented for six reports; the other two
  formats are not.
- **Write UI for purchases, suppliers, expenses and employees.** All four are
  fully modelled, seeded and readable, and the services that mutate them are
  tested, but they have no create/edit screens yet. Ingredients, recipes
  (through the cost builder), menu prices, availability and dish photos are all
  editable.
- **Photo storage assumes a persistent disk.** Uploads are written to
  `public/uploads`. That works on a VPS or container with a volume; a
  serverless deployment needs object storage (Vercel Blob, S3) instead — only
  `src/server/services/images.ts` changes.
